# v1 还是 v2？按业务场景选契约

工具有两份输出契约：默认的 **1.0**（每条写表语句一份产物，见
[`lineage.json` 输出契约](lineage-json.md)）和显式 opt-in 的 **2.0**
（整个任务脚本一份产物，见 [Task Lineage 2.0](task-lineage-v2.md)）。
本文不讲字段细节，只回答一个问题：**你的场景该用哪个。**

## 一句话判据

> **你的问题是"数据从哪来"，用 v1；你的问题是"任务干了什么"，用 v2。**

再具体一点：如果你发现自己在问带时间顺序的问题——"它是**先**清空**再**插入的吗？"
"**跑完之后**昨天的数据还在吗？"——那就是 v2 的问题。v1 是给每条写入语句拍的照片，
照片回答不了"先后"；v2 是整个任务的录像。

## 场景对照表

| 你要做的事 | 用哪个 | 一句话原因 |
| --- | --- | --- |
| **字段血缘分析**（这个字段来自上游哪些表哪些列） | **v1** | 答案就在 `end_to_end_lineage[].physical_sources` 里，拿来就能用 |
| **字段加工步骤分析**（这个指标是怎么一步步算出来的） | **v1** | 加工链（`field_mapping_chains`）、表达式、JOIN/过滤逻辑都在 v1 的证据层，还能渲染成给人看的 `mapping.md` |
| **表级依赖 / 影响分析**（改了上游表，影响谁） | **v1** | `source_tables` / `target_table` 直接可读 |
| **给数据地图 / 数据资产平台建血缘图** | **v1** | 平台按"目标表"组织资产，v1 一个目录一张表，粒度正好对上 |
| **审计一个任务改了什么数据**（删了什么、清空了什么、更新了什么） | **v2** | v1 不建模 DELETE / UPDATE / TRUNCATE，只把它们记在 `skipped_statements` 里 |
| **判断任务跑完后表是什么样**（空了？整表覆盖？只覆盖昨天分区？） | **v2** | 这是"最终状态"问题，只有 v2 的 `final_table_states` / `table_state_graph` 记录状态 |
| **排查数据丢失事故**（"表怎么空了 / 数据怎么少了"） | **v2** | 要还原语句执行顺序和每一步对表的影响 |
| **数据质量归因**（这行数据为什么消失 / 为什么没更新） | **v2** | "行还在不在"由 DELETE / MERGE 条件决定，只有 v2 的 `row_membership_sources` 区分这个 |
| **合规 / 安全审查**（敏感字段流到哪里，包括中间被删被改的路径） | **v2** | 需要完整的任务级事实，不能漏掉 v1 未建模的语句 |
| **CI 质量门禁** | 都可以 | 两边的 `--quality-policy` / `--fail-on-*` 口径已对齐（含未展开星号）；但"未建模的数据变更也要拦"只有 v2 的 balanced/strict 能做 |

## 两个典型场景的展开

**字段血缘分析 → v1。** 你想知道 `mart.customer_summary.order_count` 来自哪——打开 v1
产物，`end_to_end_lineage` 里直接写着"来自 `dwd.order_detail.order_id`，经过聚合"。完事。
用 v2 也能查到同样的答案，但你必须先做对几件事：剔除"来自表自己上一状态"的
`prior_table_state` 边（实测占一半）、用 `fold_session_scoped` 折叠临时视图、检查
`source_state`——一步做错，结论就是错的。**能用 v1 答的问题，别用 v2 自找麻烦。**

**字段加工步骤分析 → v1。** 你想向业务方解释"这个指标是先按客户分组、再算 30 天支付
金额、最后取排名第一的记录"——v1 的 `field_mapping_chains[].ordered_steps[]` 按步骤记录
每一层做了什么，每步带原始 SQL 表达式，`scope-lineage render` 还能输出人可读的
`mapping.md`。这正是 v1 设计出来干的事。

## 什么时候两个都跑

如果你的任务脚本普遍很干净（一个任务一条 INSERT），只跑 v1 就够了——这时两份契约的
信息几乎等价，v1 消费成本低得多。

如果脚本里常见**临时视图中转、多段写入、同表写多次、DELETE / TRUNCATE 穿插**，建议
两个都跑、输出到**不同目录**：日常的血缘查询、字段解释走 v1；事故排查、审计、状态
判断走 v2。

两边指的是同一条语句时，用 **`statement_id`**（形如 `stmt:002`）对上号——它是两份契约
之间唯一被指定的关联键；**不要用 `task_id`**，两边的编号口径不同，同名会静默指向不同
的语句（详见 [lineage-json.md](lineage-json.md) 顶层字段表与
[task-lineage-v2.md](task-lineage-v2.md) 的"兼容与消费"）。

## 给新消费方的建议

如果你在写一个新的消费程序、而且需求还会长（今天要血缘、明天要审计），可以直接消费
v2：它的 `statement_lineage.<statement_id>` 里嵌着每条写语句的**完整 v1 文档**，语句级
证据一样不少；反过来 v1 永远升不出任务级语义。代价是你必须按
[task-lineage-v2.md](task-lineage-v2.md) 正确处理前态边折叠、会话级关系、窗口上下文列
这几个已知易错点——那份文档一半以上的篇幅就在讲怎么别读错。
